# Venue Wrangler POS platform: repository audit and rollout plan

Verified against official documentation on 2026-10-06. This document separates published provider capability from Venue Wrangler's operational access. No restaurant or merchant access, credentials, provider sandbox response, or production provider deployment was verified.

## Repository architecture

The app is Flutter in `apps/mobile` with Riverpod, GoRouter, and Supabase Auth/Postgres. `public.venues` belongs to `public.organizations`; memberships and `app_hidden.has_venue_role` authorize managers. `public.shifts` is the existing schedule, with `staff_id`, `role_label`, UTC start/end timestamps, and scheduled/completed/cancelled status. `public.venues.timezone` supplies the business timezone. A draft/published distinction did not exist. The POS area had `pos_connections`, `pos_checks`, and `pos_outbound_commands`, plus `toast-pos` Edge Function. The function accepted a custom gateway webhook and queued menu commands, but it did not send them to Toast. Its prior real-time language was inaccurate. Square payroll OAuth is separate from Square POS scheduling and does not prove the latter's permissions.

The new migration creates connection capabilities, reviewed mappings, retained external shift IDs, normalized sales and actual time entries, schedule versions, an ordered outbox shape, conflicts, sync runs, and audit events. `request_pos_connection` lets a manager record an onboarding request; it creates an inactive connection with nine unverified capabilities and accepts no credentials. `publish_pos_schedule` is a manager-authorized database transaction: it validates readiness, location, staff and job IDs, and per-operation capabilities before snapshotting shifts and queuing jobs. `claim_pos_outbound_jobs` leases the oldest eligible operation per shift and diverts expired leases to reconciliation. Service-only completion and failure functions retain external IDs, apply retry backoff, and keep uncertain results pending reconciliation. Draft edits remain in `public.shifts`; explicit publication is the export trigger. The schedule remove action deletes local drafts and retains mapped shifts as cancelled for a later POS publication. Existing scheduling works with no POS connection. No mobile code calls provider APIs.

**Current operational limit:** no schedule worker or provider adapter has been deployed, so jobs remain pending. The `connected` readiness value and `verified_supported` capability rows must be set only after a server-side onboarding process verifies access. The UI must never imply a queued job was acknowledged by the POS. Existing historical `active` connections migrate to `configuration_required`.

Local validation on 2026-10-06 replayed the migrations and ran 34 schedule-platform and 13 legacy POS assertions in a disposable PostgreSQL 18 instance using temporary assertion helpers. Flutter scoped analysis found no issues and 13 focused POS/schedule tests passed. The unrelated notification migration requiring the Supabase `pg_net` extension was omitted because that extension is unavailable in plain PostgreSQL; this does not verify a full Supabase migration replay.

The database migrations were applied to live Supabase project `puttwjwmwrzmhpsjykuj` on 2026-10-06 Chicago time. Supabase recorded `20261007021641_pos_schedule_platform` and `20261007021847_pos_schedule_fk_indexes`. Post-deployment checks found all 12 new tables with forced RLS, the expected RPCs and grants, zero POS connections and outbound jobs, and the legacy client queue insert revoked. All 53 local migration filenames now match the 53 live migration versions. The project is on the Free plan and no restorable database backup was verified; the user chose a guarded reverse migration for this additive, initially empty POS schema. The reverse SQL is in `docs/migration/pos-schedule-platform-rollback.sql` and refuses to discard POS data. The database deployment does not constitute a mobile release, provider authorization, or a functioning delivery worker.

## Credentials, approvals, and phases

1. Obtain provider agreements, partner approvals, sandbox tenants, merchant or restaurant authorization, product/version and location identifiers, and precisely scoped credentials. Keep provider secrets in a server-only approved secret store. Do not enter them in Flutter or `pos_connections.credentials_encrypted` without a verified encryption/key-management path.
2. Validate migration and tenant authorization in a disposable database. Add a server-only onboarding service that sets connection readiness and capability evidence only after provider access is tested. Validate location, employee and job mappings by stable IDs with human review for ambiguity.
3. Build provider adapters and a lease-based worker that claims only the earliest outstanding job for each shift, reconciles uncertain writes before retry, applies provider idempotency/revision controls, records acknowledgment and external IDs, classifies rate limits/permanent errors, and dead-letters exhausted jobs. Schedule inbound backfills and reconciliation with checkpoints. Store only redacted errors.
4. Implement Toast and Square adapters from current endpoint references in approved sandboxes. Square needs draft write then publish, including deletion publication; Toast needs serialized PUT/DELETE and time-entry checks before delete. Test expired tokens, duplicates, lost acknowledgment, concurrent edits, external conflicts, overnight shifts, DST and partial failures.
5. Implement remaining products only after each operation and access path is verified. Pilot with a controlled merchant, compare sales definitions and timecards to source data, then deploy with rollback and monitoring.

## Deployment and rollback

Apply migrations in timestamp order to a disposable database and run pgTAP plus Flutter tests first. The initial live POS schema was applied with zero POS connections and a guarded reverse migration because the Free plan has no managed backup. Before any data-bearing migration or provider pilot, create and verify a restorable backup. Deploy the app UI with connections held at `configuration_required`; then deploy onboarding/worker components and enable verified capabilities for a pilot. To stop outbound traffic, pause the worker and set readiness to `configuration_required` without discarding mappings, jobs, or audit records. Do not roll back by dropping the new tables while jobs or external IDs need reconciliation.

## Access-blocked work

Provider credentials, partner approvals, merchant authorizations, sandboxes, and a production secret mechanism were not supplied. Accordingly no adapter, inbound worker, webhook verifier, schedule worker, live connection, or production provider response is claimed here. Connection setup, mapping review/actions, retries, disconnect, and reconciliation UI need the server workflows above before they are safe to enable.
